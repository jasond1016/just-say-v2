# 2026-10-19 本地翻译模型：低占用候选

研究日期：2026-10-19。范围：只读官方模型卡、官方技术报告、Hugging Face 文件清单和本仓库源码。选型当时没有下载权重，也没有在本机翻译。随后的同机实测写在 [Index-Translate-2B 和识别同时跑](2026-10-19-index-translate-probe.md)。识别换成 SenseVoice 之后，同一批句子又跑了 Index 和 Hy-MT2，写在 [SenseVoice 加两套翻译](2026-10-19-sensevoice-mt-probe.md)。厂商自己的表是作者自报，不是 JustSay 的成绩。本文不重开识别模型选型，也不推翻同日笔记里对 Confucius4-T3PO 的结论。

## 结论

**有一个值得做下一轮实验的低占用候选，没有一个可以原样接上现有请求就当成理想默认。**

最接近的是哔哩哔哩 2026-09-30 发布的 [Index-Translate-2B](https://huggingface.co/IndexTeam/Index-Translate-2B)。它是翻译专用模型，不是同尺寸通用对话模型；官方 GGUF 的 Q4_K_M 为 1.31 GB；日语在其 22 个核心语言里。作者在自己的技术报告里把它和同代 1.8B–2B 模型放在同一张表上，FLORES-200 的 COMET-22 是 0.8655，高于 Hy-MT2-1.8B 的 0.8522，也明显高于通用底模 Qwen3.5-2B 的 0.6983。

它还不是产品默认，原因有三条：

1. 官方例子必须关掉思考，并使用一条中文用户提示。本仓库的请求两者都不是。
2. 作者表上的 WMT26 裁判分是 60.26，同一张表里 GPT-5.6-Sol 是 89.10。COMET 接近前沿，裁判分没有接近。
3. 日语没有单独公布的分数。核心语言名单里有日语，不能据此写成日译已经测过。

腾讯 2026-05-21 的 [Hy-MT2-1.8B](https://huggingface.co/tencent/Hy-MT2-1.8B) 是同一量级的备选：Apache-2.0，Q4_K_M 文件 1,133,080,448 字节约 1.06 GiB，语言表含中文、英文、日语。它比 Index-Translate-2B 更容易按「只输出译文」来提示，但在 Index 的作者表上全面落后，低资源方向的偏题率是 54.2%。

不要把通用 2B 对话模型、云端 Qwen-MT、TranslateGemma-4B、7B 级翻译模型或 T3PO 当成这个句子级路径的低占用候选。

## 当前翻译路径

这些是源码行为。

| 面 | 现在怎么做 |
|---|---|
| 时机 | 只翻译已提交块。草稿和预览不进翻译。见同日运行时笔记 |
| 接口 | `POST {base}/chat/completions`。提供方只有 `openai-compatible`。未配置模型名时，客户端默认模型字符串是 `gpt-4o-mini` |
| 提示 | 固定英文 system：「You are a translation engine... Return only the translated text...」。用户消息是 `Source language`、`Target language`、`Text`。源语言可以是 `auto`，设置里的默认目标语言是 `en` |
| 采样 | 请求里只有 `temperature: 0`。不发送 `max_tokens`、`top_p`、`top_k`，也不发送 `chat_template_kwargs` |
| 失败 | 超时默认 10 秒。`choices[0].message.content` 为空则抛错。思考开关只对 DeepSeek 聊天端点附加 |
| 显存邻居 | Qwen3-ASR-1.7B 的 vLLM sidecar 默认 `gpu_memory_utilization=0.55`，为的是 16 GB 卡上给别的 GPU 工作留余量 |

翻译不是 Engine Profile，也不是 Runtime Family。换模型的现成入口是操作者自己的 endpoint 和 model，不是新 sidecar。一个自定义翻译协议仍然是新集成。

## Index-Translate-2B 为什么排在前面

官方模型卡和 [技术报告](https://arxiv.org/html/2609.40181) 写的是同一套作者评测：贪心解码，思考在模型支持时关掉，主表上下文 16,384。FLORES-200 是 21 种语言、420 个方向、126,000 条，方向等权。下面只摘和「小、专、能不能打过同尺寸通用模型」直接相关的格，全部是作者自报。

| 模型 | FLORES COMET-22 | WMT24++ COMET-22 | WMT26 裁判（0–100） | 低资源 FLORES 偏题率 |
|---|---:|---:|---:|---:|
| Index-Translate-2B | 0.8655 | 0.8489 | 60.26 | 4.2% |
| Hy-MT2-1.8B | 0.8522 | 0.8401 | 49.35 | 54.2% |
| Qwen3.5-2B | 0.6983 | 0.6933 | 32.11 | 39.1% |
| TranslateGemma-12B | 0.8732 | 0.8524 | 71.19 | 1.7% |
| GPT-5.6-Sol | 0.8650 | 0.8469 | 89.10 | 10.4% |
| Gemini 3.5 Flash Lite | 0.8750 | 0.8497 | 79.52 | 3.3% |

COMET 在 FLORES 上把 2B 专用模型和报告里的前沿模型放进了同一档。WMT26 的模型裁判没有。两列不能互相换算。低资源偏题率说明 Hy-MT2-1.8B 的弱点在覆盖面，不在中英这种高资源方向的 COMET 差距；中英日正好是高资源，所以这列不能单独用来淘汰 Hy-MT2。

日语的位置：附录语言表把 `ja` 放在 22 个核心语言里。MTNT 的说明是英语与法语、日语双向，但公布的是五个领域的混合分，不是日语单列。本轮没有日译中或中译日的独立数字。

资源：文本翻译不需要视觉投影。官方写 BF16 大约从 8 GB 起，这和识别 sidecar 的 0.55 预留挤在同一张 16 GB 卡上不合适。Q4_K_M 1.31 GB 才是和「留下的显存」同一量级的文件。配置里的 `max_position_embeddings` 是 262144；官方自己的短文本例子把服务上下文降到 4096。按 256K 去分配 KV，会把这个小模型重新变成大显存用户。

## 为什么现有客户端还接不上论文分数

Index 的官方客户端只发一条用户消息，提示形如「请将以下文本翻译为{目标语言}，直接输出翻译结果，不要进行任何解释。」源语言为 `auto` 时不写源语言名。解码 temperature 0、`max_tokens=1024`，并用 `chat_template_kwargs.enable_thinking=false` 关掉思考。示例还要剔除内容里的 `</think>`。

本仓库每次都发英文 system，用户消息是另一套字段，temperature 虽是 0，但不发送 `max_tokens`，也不发送关思考的字段。空内容直接失败，10 秒超时。思考若写进 `content`，译文里会带上思考；若思考占满预算而 `content` 为空，请求会被当成错误。

Hy-MT2 的模型卡写明没有默认 system prompt，推荐 temperature 0.7 而不是 0，提示同样是单条用户消息。它的例子没有思考开关。因此它和当前请求的表面距离更近，已公布的对照分数却更低。两种差距都还没有在本仓库的提示上测过。

所以实验边界是：本地 OpenAI 兼容服务自己关掉思考、限制上下文、限制显存，再用当前请求打几句中、英、日。通过之前，不改产品代码，也不把论文分数写成 JustSay 的分数。

## 其余候选为什么不选

**Hy-MT2-1.8B 留作备选，不留 1.25-bit。** 模型卡称 AngelSlim 1.25-bit 把存储降到 440 MB，并在 Apple A15 上比传统 4-bit 快 1.5 倍。这是存储和一块手机芯片上的速度，不是翻译质量。上一代 HY-MT1.5 的技术报告已经写过：FP8 的 XCOMET 与原模型接近，GPTQ Int4 明显下降，例如 FLORES 中外方向 0.8361 降到 0.8060。Hy-MT2 本轮没有对应的量化质量表，不能把 440 MB 当成无损。HY-MT1.5 的 0.18 秒也只属于那份报告里的 100 句中译英，报告没有写明那次用的显卡，不能挪到 4060 Ti 或 Hy-MT2。

**HY-MT1.5 的许可证更窄。** 2025-12-30 的社区协议排除欧盟、英国和韩国，并把超过 1 亿月活的商业使用留给腾讯另行许可。Hy-MT2 的模型卡写成 Apache-2.0。新实验没有理由退回 1.5，除非机器上已经有那份权重。

**TranslateGemma-4B 的接口对不上。** 模型卡要求用户内容是仅含一个元素的列表，并带 `source_lang_code` 和 `target_lang_code`；不支持的语言代码会在套模板时直接报错。4B 的 WMT24++ 汇总是 MetricX 5.32、COMET 81.6，技术报告另给 COMET22 从基线 77.2 到 80.1。分语言附录里能读出的 en→ja_JP、en→zh_CN 只有更大尺寸的列。人工 MQM 没有 4B，12B 的日译英是那张 10 个方向表里最差的一格（15.7，越低越好）。12B 的 BF16 也不属于这张卡的余量。

**MiLMMT-46-1B 更小，但证据停在一张图。** 语言名单含日语和中文，官方温度也是 0。提示必须使用它规定的语言全名，例如 `Chinese (Simplified)`，并是「Translate this from ... to ...」的补全格式。模型卡没有给出可引用的分数表。

**Qwen-MT 不是本地权重。** 2026-10-11 的官方文档仍是云端三档，并写明不支持 system。它不能回答「本地、省资源」。

**7B 与同传模型维持原结论。** Seed-X 只有 7B 系列。Hy-MT2-7B、TranslateGemma-12B 在作者表上更高，但已经离开「和 1.7B 识别共存」的范围。T3PO 仍是中英同传状态机，不是这句提交后再译的替换，GGUF 也放不进剩下的显存。

## 和现有决策的关系

- 维持 ADR-0001：翻译继续是识别旁边的凭据和端点，不新开 Runtime Family。
- 维持同日笔记：翻译只吃已提交块；T3PO 只在同传需求出现后另评。
- 本轮不改默认端点，不下载权重，不把任何本地模型写进 Engine Profile。

## 测量之前不要下的结论

- Index 与 Hy-MT2 的分数都来自 Index 技术报告的作者评测，或各家模型卡的自我声明。没有第三方复现，也没有 JustSay 的中英日句子。
- FLORES 的 21 种语言是否包含日语，报告这一段没有逐个点名。能确定的是日语在核心语言表里，以及 MTNT 的混合分里含英日。
- 当前英文 system 加字段式用户消息，在 temperature 0、不关思考时会得到什么，没有任何官方数字。
- 1.31 GB 或 1.06 GiB 是权重文件大小，不是进程显存。上下文若按 256K 分配，文件大小不再代表占用。
- 10 秒超时只说明产品预算。本轮没有 4060 Ti 上的句延迟。
