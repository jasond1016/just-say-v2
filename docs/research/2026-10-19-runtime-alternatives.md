# 2026-10-19 运行时替代与优化：对照当前 JustSay 实现

研究日期：2026-10-19。初稿对照官方模型卡、官方仓库和当前源码。同日后来补上的本机实测写在下文，那些分数才是 JustSay 这台机器上的结果。2026-10-01 的有道模型研究和日语 FLEURS pilot 仍然有效。

## 结论

**不要替换现有默认链路。** `local-fast` 继续用 SenseVoiceSmall，`local-accurate` 继续用 Qwen3-ASR-1.7B 的 vLLM sidecar。Qwen3-ASR 仍然是 0.6B / 1.7B 这两个尺寸。

**Fun-ASR-Nano-2512 和 Confucius4-R2T2 都不转正。** 不接入产品 Runtime Family，也不再为它们保留实验 sidecar。Fun-ASR-Nano 在同一套 32 条日语、英语试点上的最终文本是日语字错误率 14.52%（数字折叠后 13.54%）、英语词错误率 19.35%（数字词折叠后 19.20%），差于当时的 Qwen（日语 7.45% / 6.99%，英语 5.61% / 4.87%）和 SenseVoice 日语（6.80% / 6.48%）。R2T2 日语试点自动语言字错误率 32.275%，强制日语后 8.684%，仍差于当时的 Qwen 7.45% 和 SenseVoice 6.80%。

值得继续看的是已经在用的模型，而不是再开一条识别 sidecar。翻译继续按已提交块调用通用对话接口；只有产品要做同声传译时，才单独评估 T3PO。

同一套日语 650 条、英语 647 条上，Qwen3-ASR-0.6B 用和 1.7B 相同的流式终稿设置（1.0 秒一块，unfixed 4，token 5，语言不指定）差于 1.7B。日语男声 571 条字错误率 11.64%（3373/28968），数字折叠后 11.34%（3289/29011）；1.7B 是 8.44% / 8.05%。英语词错误率 4.95%（714/14427），数字词折叠后 4.70%（678/14425）；1.7B 是 4.45% / 4.13%。`local-accurate` 继续用 1.7B。0.6B 仍是已有的 lite 选项，不升成默认识别。

同一条 17 分 13 秒的日语播客（YouTube `C9VabhxOPbA`，自动滚动字幕，不是人工稿；按 600 毫秒静音切成 194 段，单段最长 25 秒）上，对照字幕的字错误率是 SenseVoice 7.68%（435/5662）、Qwen3-ASR-1.7B 5.76%（326/5662）、Qwen3-ASR-0.6B 5.17%（293/5662）。数字折叠后分别是 7.36%、5.33%、4.68%。0.6B 更接近这份自动字幕，不能推翻上面的朗读全集：自动字幕会漏词，也会丢掉「まあ」「うん」，0.6B 同样少写这些口气词。开头字幕是「ゆゆしのお時間」，三个模型都听成了「ゆゆの日本語ポッドキャストのお時間」。同一份 SenseVoice 文本去掉情绪和事件表情后，字错误率从 7.68% 降到 7.40%（419/5662），数字折叠后从 7.36% 降到 7.08%（401/5662）。用改过的服务重跑时，194 段里有 20 段在去掉表情后文字仍不同，其中有「10」变成「100」，所以重跑分数不能单独当成这次改动的效果。SenseVoice 这条解码没有 beam。在同一次重跑（自动语言、开启数字正规化，7.59% / 7.28%）上再改参数：强制日语是 7.63%（432/5662）/ 7.31%，禁用未知情绪是 7.72%（437/5662）/ 7.38%，关掉数字正规化是 6.61%（374/5662）/ 6.29%。前两个没有收益。关掉数字正规化会改变识别本身，不只是数字写法；对照自动字幕更好，但样例里既有「でこ」收成「で」，也有「なんか」收成「なか」。产品默认仍开着数字正规化。

## 当前实现里和选型有关的事实

这些是源码行为，不是模型卡宣传。

| 面 | 现在怎么做 |
|---|---|
| 对外可选的 Engine Profile | `local-fast` → `iic/SenseVoiceSmall`；`local-accurate` → `Qwen/Qwen3-ASR-1.7B`；`local-accurate-lite` → `Qwen/Qwen3-ASR-0.6B`。云端两项未暴露，而且 runtime family 仍写成 sensevoice |
| Qwen 宿主 | Linux / WSL / Docker 上的 vLLM。原生 Windows 直接拒绝启动。默认 `chunk_size_sec=1.0`、`unfixed_chunk_num=4`、`unfixed_token_num=5`，与官方流式 demo 的默认参数一致；官方 Python API 的默认值则是 2.0 秒 / 2 / 5 |
| Qwen 草稿 | 每次推理返回整句最新假设。服务用前后两次文本的公共前缀充当 `stableText`，其余当 `previewText`。这不是模型单独交出的已提交前缀 |
| Qwen 语言 | 会话消息里的 `language` 被存下来，但 `init_streaming_state()` 没有把语言传进去 |
| Qwen 分句 | Silero VAD，静音约 600 ms 结束，单句最长 25 秒后强制提交并换一句 |
| SenseVoice | 按键听写只在松开时整段识别。会议按能量检测说话，每约 300 ms 把当前句写成临时 wav 再整段识别，草稿全部放在 `previewText`，`stableText` 为空。连续静音 6 个 100 ms 包后提交 |
| 翻译 | 每个已提交块单独请求 OpenAI 兼容的 chat completions。空响应视为错误 |

音频仍是 16 kHz、单声道、PCM16，约 100 ms 一块。本地 profile 不提供词级时间戳和说话人分离。

## 不换模型时的优化

按「值得测量」排序。每一项在测量前都不改默认值。

### 1. 先看清单句变长之后的重算

Qwen 源码写明：新块到达后拼进 `audio_accum`，把至今为止的音频重新交给模型。Fun-ASR 的实时服务把同一问题写得更直白：不截断的话，长句每次从句首重编码，复杂度随句长平方增长，所以它把中间结果窗口默认限制在最近 15 秒；最终提交不受这个窗口影响。

本仓库已经在 25 秒强制换句。这和「不能让一句无限变长」是一致的。2026-10-19 在 4060 Ti 上按当前 1 秒块量过逐步解码：日语在第 5、15、25 秒是 172、205、154 毫秒，英语是 150、160、298 毫秒。单步没有接近 1 秒，不必为此缩短 `JUSTSAY_QWEN_MAX_UTTERANCE_MS`。

### 2. 用户明确指定语言时，把语言传进流式状态

`init_streaming_state(language=...)` 会强制文本语言，和离线 `transcribe()` 同一套校验。当前服务收下了会话语言，却总是自动识别。10 月 1 日的日语实验已经记录过这个差异。产品主场景是中英来回切换，自动识别应继续作为默认。

2026-10-19 用同一套 32 条试点对照过「传入 / 不传入」，测完后把接线撤掉，默认仍不传语言。英语 32 条的转写与自动识别逐条相同，词错误率仍是 5.61%（38/677）。日语 30 条编辑距离不变，1 条多 1 处编辑，另 1 条（`fleurs-ja-test-8922261396806111795`）从 2 处编辑变成同一句式的重复循环，合计 358 处编辑，整批字错误率从 7.45% 变成 30.59%。强制语言没有少掉串语错误，却给日语加了一种重复失败。

### 3. 块长是延迟和质量的旋钮，现在的默认值是有出处的

官方流式 demo 默认 1.0 秒 / unfixed chunk 4 / unfixed token 5，与本仓库相同。官方示例脚本用的是 2.0 秒 / 2 / 5，那也是 API 默认值。更长的块通常更稳，但首段草稿不可能早于凑满一个块。10 月 1 日日语 pilot 的首草稿中位数约 2.1 秒，和「1 秒音频块 + 推理」是同一量级，不能靠把块改成 160 ms 就宣称达到 R2T2 那种延迟。

2026-10-19 已在同一套日语、英语试点上对照过两组参数，默认保持 1.0/4/5。

官方 API 的 2.0 秒 / unfixed 2 / token 5：日语字错误率 7.45% → 7.19%，英语词错误率 5.61% → 5.76%。英语首条草稿中位从 1.15 秒变成 2.29 秒，首段稳定文本从 2.20 秒变成 4.31 秒。日语首段稳定文本从 3.33 秒变成 4.46 秒。回退变少，可用文本更晚。

只把 unfixed 从 4 改成 2、块长仍是 1.0 秒：日语字错误率升到 8.81%（136/1543），英语词错误率 6.06%（41/677），数字词折叠后仍是 4.87%（33/677）。首条草稿、首段稳定文本和回退次数都与 1.0/4/5 同一量级。缩短未固定尾巴没有换来更早或更稳的草稿。

同一天用全部日语 650 条、英语 647 条，按 1 秒一块看模型文本何时从空变成有字。sidecar 在模型文本一非空就发草稿。英语 72.6%（470/647）在第 1 秒就有字，中位 1.0 秒。日语里 79 条女性录音的整段响度大约只有男性的百分之一，第 1 秒出现的字符串并不是该句内容；32 条试点里第 1 秒就有草稿的 12 条全是这批。其余 571 条男性录音只有 2 条在第 1 秒有字，中位要到第 3 秒。第一秒响度已经正常的 257 条里，141 条要到第 3 秒才出字。日语首字晚，是第一秒的解码结果为空。之前 2.1 秒的试点中位数被那 12 条极轻录音提前了。

2026-10-19 用全部日语 650 条、英语 647 条重算了同一套 1 秒块流式的最终文本。语言仍不传入。日语 32 条试点里有 30 条和当时 sidecar 的最终文本相同。全集日语字错误率 8.69%（2839/32655），数字折叠后 8.32%。其中正常响度的 571 条男性录音是 8.44% / 8.05%；79 条极轻的女性录音是 10.69% / 10.46%。英语全集词错误率 4.45%（642/14427），数字词折叠后 4.13%（596/14425）。32 条试点的日语 7.45%、英语 5.61% 不能代表全集。

### 4. 草稿稳定性已经和翻译错开，保持这个边界

Qwen 的 `state.text` 是最新整句假设，公共前缀启发式仍可能回退。10 月 1 日观察到同块稳定前缀回退 9 次。翻译只吃已提交块，这是对的。不要把 `previewText` 送进翻译。

SenseVoice 会议草稿把整句放进 `previewText`，同样不应翻译。它的「streaming: true」表示服务会推草稿，不表示声学编码器是增量的。

### 5. 时间戳留在会后，不进实时路径

Qwen 官方写明流式推理不跑 forced aligner。`Qwen3-ForcedAligner-0.6B` 是离线对齐，最长约 5 分钟，11 种语言，作者用 AAS 毫秒和 MFA、NFA、WhisperX 比较。若以后历史记录需要词级时间，应对**已提交文本和已保存音频**做离线对齐，并把它当成另一个 Runtime Family 或离线任务。实时 sidecar 继续报告 `wordTiming: false`。

说话人分离同样不进默认识别。Fun-ASR 实时服务的说话人是 beta，SenseVoice 的情绪标签也不是说话人。NVIDIA 的 Sortformer 绑在 NIM 上，而且中文相关档不支持 WSL2。

## Fun-ASR-Nano 的实验结果

2026-10-19 用 `FunAudioLLM/Fun-ASR-Nano-2512`（funasr 1.4.16，语言不指定，ITN 开，720 毫秒块，回退 8 字）在同一套日语、英语试点上取了 `streaming_generate` 的最终文本。这个接口是整段一起算完再逐块吐出，所以只比较错误率。日语字错误率 14.52%（224/1543），数字折叠后 13.54%（209/1544）。英语词错误率 19.35%（131/677），数字词折叠后 19.20%（130/677）。同一批上 Qwen 自动识别是日语 7.45% / 6.99%、英语 5.61% / 4.87%，SenseVoice 日语是 6.80% / 6.48%。**不转正，不新开产品 sidecar。** 用的是 Nano，不是 31 语言的 MLT-Nano。

## 翻译

当前「一句提交后再翻译」适合会后阅读和按键听写。它允许整句重译，也避免把还会改的预览锁进译文。

Confucius4-T3PO 仍是中英同传的对口模型，不是更好的通用翻译器。官方协议是两段状态：`STREAMING_HISTORY` 放已提交的原文和译文，`CURRENT_INPUT` 放还没提交的原文。空响应表示 WAIT，非空表示写出一段且不再改写。现有客户端把空内容当成异常，所以不能只改模型名。

资源上也不该和 1.7B 识别挤在一张 16 GB 卡上。GGUF 的 Q6_K 约 12.1 GB，Q5_K_M 约 10.5 GB。识别 sidecar 已经按 0.55 的显存占用预留。同传若要做，应是另一个 Remote Service，默不捆绑。官方也写了日译中并未训练、只是观察到一定泛化，不能当成日语产品路径。

Canary 的语音翻译是离线、多语言方向，和「边说边出译文」不是同一功能。

## 和现有决策的关系

- 维持 ADR-0001：新模型用新 sidecar，健康检查仍报告真实 Runtime Identity。原生 Windows 上跑 Qwen，与 `service.py` 里的平台拒绝相冲突，本文不建议打开。
- 维持 10 月 1 日结论，并在 2026-10-19 关闭转正：R2T2 不替换日语或默认识别；Fun-ASR-Nano 同样不转正。T3PO 只在同传需求出现后评估。
- 云端 profile 今天没有真实云识别实现。接一家云 API 不能改善本机按键听写，也不该为了云端把本地 sidecar 收成一个多模型入口。

## 测量之前不要下的结论

- Fun-ASR-Nano 的日语、英语最终文本已经在本机同一套试点上测过，见上一节；FireRedASR2、Parakeet、GLM 的错误率和尾音延迟仍然没有本机复现。
- Qwen 官方流式分数没有公布 chunk 参数，不能反推本仓库 1.0/4/5 的会议表现。
- 10 月 1 日的日语数字来自 32 条朗读 pilot，不是 650 条全集，也不是中英混说。
- 本轮没有把 Kyutai、Moonshine 列成候选：没有见到官方的中英流式模型卡足以和上表比较。若要补，先读模型卡，再决定是否实验。
